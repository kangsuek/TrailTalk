# 음성 합성(TTS) 신뢰성 개선 계획

> 상태: **해결 완료(2026-10-21)** — `.env`의 `TTS_MODEL=tts-1` 적용으로 합성 멈춤이 사라졌고(검색 답변 5턴 재시도·실패 0건) 사용자가 일상 사용에 문제가 없음을 확인했다. 아래 개선 작업은 필요가 없어져 종결했다. 작성(2026-10-20): 폰 대화에서 "텍스트는 길게 나오는데 음성은 일부만 읽는" 문제가 SR-07(시도당 8초 × 3회 재시도) 적용 뒤에도 계속되어, 관련 소스를 분석하고 원인을 실험으로 가른 뒤 개선 방안을 정리했다. 검색·응답 개선 계획서([search-response-improvement.md](search-response-improvement.md))의 SR-07 후속이다.
> 작업은 이 문서의 ID(`TR-01` …) 단위로 진행한다. 소스를 고치기 전에 계획을 보고하고, 커밋 전 서브에이전트 diff 리뷰를 한다.

## 1. 증상과 근거

| 관찰 | 값 |
|---|---|
| 증상 | 화면에는 모든 문장이 나오지만 일부 문장은 소리가 나지 않는다. 첫 소리도 늦어진다 |
| SR-07 전(세션 `f67c`) | 3개 턴에서 문장 4~5개 중 2~3개가 `tts_timeout`(15초). 첫 문장 합성 15초 3회 |
| SR-07 후(세션 `9c33`, `c1c9`) | 재시도 1/3, 2/3이 연달아 발생. 한 문장은 3회 모두 멈춰 소리가 빠짐. 한 턴의 합성 대기 27.7초 |
| 정상 응답 | 대개 1~3초(중앙 2.0초) |

## 2. 소스 분석 (합성 경로)

호출 순서: `conversation.py` `queue()` → `Speech.synthesize` → `OpenAiTts.synthesize` → `openai_http.post` → OpenAI `/audio/speech`.

| 위치 | 현재 동작 | 문제점 |
|---|---|---|
| `app/main.py` 64행 | 서버 하나가 `httpx2.AsyncClient()` 기본값을 STT·TTS와 공유 | 연결 문제 아님(실험 3.2 참고). 변경 불필요 |
| `app/voice/tts.py` | 모델 `gpt-4o-mini-tts` + 말투 지시(`instructions`), 본문 전체를 받은 뒤 반환 | 모델이 응답을 시작하지 않고 멈추는 일이 잦다(3장) |
| `app/voice/openai_http.py` | 시도당 8초 제한, 총 3회 순차 재시도(SR-07). 시간 초과는 `TimeoutException` 하나로 묶임 | 8초는 정상 응답(최대 3초대)에 비해 너무 길어 한 번 멈추면 8초를 버림. 연결/읽기 단계를 구분하지 않아 로그로 원인을 못 가림 |
| `app/voice/speech.py` | 동시 합성 3개 세마포어, 실패 시 `None`(소리 없음), 안내 문구 캐시는 실패를 캐시하지 않음 | 멈춘 요청이 재시도 내내 슬롯을 잡아(최대 약 24초) 뒤 문장 합성이 늦어진다 |
| `conversation.py` `queue`/`next_sentence` | 문장마다 합성 작업을 동시에 띄우고, **맨 앞 문장 소리가 올 때까지 기다린 뒤** 순서대로 보냄 | 맨 앞 문장이 멈추면 이미 끝난 뒤 문장도 함께 밀린다(머리 막힘) |
| `conversation.py` ToolStarted(약 806~833행) | 도구 시작 전에 남은 문장을 모두 기다리고, **검색 안내 음성(`speech.cached`)을 인라인으로 await** | 안내 합성이 멈추면 CLI 이벤트 읽기 자체가 최대 24초 멈춘다. 안내는 실패하면 캐시되지 않아 같은 일이 반복됨 |
| `conversation.py` ToolCalled/ToolFinished | 도구 경계마다 대기 중인 문장을 모두 비운다 | 합성 지연이 검색 이벤트 전달 지연으로 번진다 |
| `web/src/platform/audioOutput.ts` | `audio`가 `null`인 문장은 조용히 건너뛰고 문장 번호만 보고 | 서버 주석(`speech.py` 머리말)은 "글로 보이거나 기기 TTS로 대신한다"지만 **기기 TTS 대체는 구현돼 있지 않다**. 실패하면 완전한 무음 |
| 관측 | 로그에 시도 횟수·모델·문장 길이·소요 시간 없음. 턴 로그는 `synth_wait`만 | 소리가 빠진 빈도를 셀 수 없다 |

## 3. 원인 확정 실험 (2026-10-20, 실제 OpenAI 호출 약 190회)

### 3.1 결과 요약

| 실험 | 조건 | 결과 |
|---|---|---|
| 1 | 긴 문장 20개 동시, 제한 20초 | 14개 성공(중앙 2.6초, 90% 3.5초, 최대 6.9초), **6개(30%) 20초에도 무응답** |
| 2 | 변수 비교(각 12, 순차 10): 기준 / IPv4 전용 / `instructions` 제거 / `tts-1` | 기준 10/12, IPv4 10/12, `instructions` 없음 6/12(개선 없음), **`tts-1` 12/12**, 연결 재사용 순차 9/10. 실패는 모두 `ReadTimeout` |
| 3 | 모델별 30회(동시 3, 제한 12초) | `gpt-4o-mini-tts` 26/30(**4개 무응답, 모두 응답 헤더 전**), `tts-1` 30/30(최대 3.8초), `tts-1-hd` 30/30(최대 8.0초) |
| 4 | 문장 5종 × 12회, 제한 6초 | 문장별 멈춤 2, 2, 1, 3, 3 /12 (짧은 "잠깐 찾아볼게요!"도 3/12). 합계 11/60(약 18%). 몰려서 발생하는 구간이 있음 |

### 3.2 결론

1. **원인은 OpenAI `gpt-4o-mini-tts`가 요청을 받고 응답을 시작하지 않고 멈추는 것**이다(응답 헤더 전 `ReadTimeout`). 응답이 시작되면 빠르다(최대 3초대).
2. 연결·네트워크 문제가 아니다: 실패는 모두 읽기 단계, IPv4 전용·연결 재사용으로 달라지지 않았다.
3. 문장 내용과 무관하다(짧은 문장도 같은 비율). 말투 지시 제거도 효과가 없다.
4. 멈춤 비율은 오늘 약 13~30%이고 시간대에 따라 몰린다. 같은 모델이라도 일시 장애일 수 있어 비율은 변한다.
5. **`tts-1`·`tts-1-hd`는 0/72로 멈추지 않았다.** `tts-1`은 응답도 빠르다(중앙 2.2초). 대신 `instructions`(말투 지시)를 받지 않아 캐릭터의 밝은 말투 표현이 약해진다.

## 4. 개선 방안

### 4.1 선택지 비교

| # | 방안 | 효과 | 비용·위험 |
|---|---|---|---|
| A | **시도당 제한을 짧게**(8초 → 4.5초) | 한 번 멈춘 문장의 복구가 약 10초 → 약 6.5초. 설정 한 줄 | 정상 응답이 가끔 4.5초를 넘기면 불필요한 재시도(+). 최대 3.8초 관측 |
| B | **헤징**: 첫 요청이 3초 안에 응답하지 않으면 끊지 않고 둘째 요청을 **동시에** 보내고 먼저 오는 쪽을 쓴다 | 멈춘 문장 복구 약 5초. 연속 멈춤 확률 감소 | 호출 +20~30%(소액). 구현이 복잡(취소·정리) |
| C | **대체 모델**: 마지막 시도는 `tts-1`(0/72 멈춤)로 보낸다 | 거의 확실히 소리가 난다. 최악 8초대 | 그 문장만 말투가 약해져 목소리 결이 다를 수 있다. `tts-1`이 못 받는 보이스는 매핑 필요 |
| D | **동시 합성 3 → 6** | 멈춘 요청이 슬롯을 잡아도 뒤 문장이 막히지 않음 | 호출 동시성 증가(제한 낮음) |
| E | **검색 안내 음성 사전 합성**(앱 시작·보이스 변경 때 캐시에 넣고, 인라인 await 제거 또는 2초 상한) | 검색 시작이 합성에 막히지 않음 | 시작 때 호출 1회 |
| F | **기기 TTS 대체 재생**: 서버가 소리 없이 문장을 보내면 클라이언트가 브라우저 음성(`speechSynthesis`)으로 읽는다 | 서버 합성이 끝내 실패해도 **빠짐없이** 읽힌다 | 목소리가 달라진다. 끼어들기(정지)·재생 비율 연동 필요, 클라이언트 변경 중간 규모 |
| G | **관측 강화**: 시도·모델·문장 길이·소요·단계(연결/읽기) 로그, 턴 로그에 재시도·실패 수 | 효과 측정과 회귀 확인 | 로그 몇 줄 |
| H | **즉시 우회**: `.env`의 `TTS_MODEL=tts-1`로 바꾼다(코드 변경 없음) | 합성 멈춤이 사라진다(실험 0/72) | 말투 지시 미적용(밝은 톤 약화). 보이스는 `nova` 등 지원 목록 안에서만 |

### 4.2 권장안 (단계별)

1. **1단계 — 측정과 기본 개선 (TR-01, TR-02)**: 관측 강화(G) + 시도당 제한 단축(A, 4.5초) + 동시 합성 증가(D) + 검색 안내 사전 합성(E). 모두 서버 설정·소규모 코드다.
2. **2단계 — 복구 시간 단축 (TR-03)**: 헤징(B) + 마지막 시도 대체 모델(C). 멈춘 문장 복구를 약 5초, 완전 실패를 거의 0으로 줄인다.
3. **3단계 — 무음 방지 최후 수단 (TR-04, 선택)**: 기기 TTS 대체 재생(F). 서버가 끝내 못 만든 문장을 읽어 준다.
4. **즉시 우회 (H)**: 개선 전에 바로 쓰고 싶으면 `.env`에서 `TTS_MODEL=tts-1`. 캐릭터 말투와의 교환이라 사용자가 결정한다.

## 5. 작업 목록

| ID | 작업 | 상태 | 커밋 |
|---|---|---|---|
| TR-01 | **관측 강화**: `openai_http.post` 로그에 시도 번호·모델·문장 길이·소요·단계(연결/읽기/풀)를 남기고(문장·본문은 제외), 턴 지연 로그 한 줄에 `tts_retries`·`tts_failed` 수를 더한다. 시간 초과 예외 종류(`ConnectTimeout`/`ReadTimeout`)를 구분해 로그 | 종결(해결됨, 미구현) | |
| TR-02 | **기본 개선**: `tts_timeout_s` 8 → 4.5, `MAX_CONCURRENT` 3 → 6, 검색 안내 음성은 앱 시작·보이스 변경 때 캐시하고 `ToolStarted`의 인라인 합성은 캐시 적중이 아니면 2초 상한으로 건너뛴다 | 종결(해결됨, 미구현) | |
| TR-03 | **헤징 + 대체 모델**: 첫 요청이 `tts_hedge_after_s`(기본 3초) 안에 응답이 없으면 끊지 않고 둘째를 동시에 보내고, 총 시도(`tts_attempts`) 중 마지막은 `tts_fallback_model`(기본 `tts-1`)로 보낸다. 먼저 성공한 쪽을 쓰고 나머지는 취소한다. `tts-1`이 받지 않는 보이스는 가장 가까운 지원 보이스로 매핑 | 종결(해결됨, 미구현) | |
| TR-04 | **기기 TTS 대체 재생(선택)**: 소리 없이 온 문장을 `speechSynthesis`로 읽고, 끼어들기 정지·`sentence_played` 보고와 연동한다. 서버 쪽 계약(`audio: null`)은 그대로 | 종결(해결됨, 미구현) | |
| TR-05 | **검증**: 모의 멈춤 단위 테스트(첫 요청 지연·연속 멈춤·취소), 실제 합성 60회 재측정(수정 전 약 18% → 목표 1% 미만), 폰에서 검색 질문 3회로 소리 누락 0건 확인 | 완료(폰 대화 5턴 합성 재시도·실패 0건 확인) | |

### 5.1 TR-03 설계 메모

- 시작: 요청 1을 보낸다. `hedge_after_s`(3초) 안에 응답 **헤더**가 오지 않으면 요청 2를 추가로 보낸다. 요청 3(대체 모델)은 6초에 보낸다. 어느 하나가 성공하면 나머지는 `cancel()`한다.
- 실패 시: 모든 요청이 오류로 끝나면 마지막 오류로 `tts_timeout`/`tts_failed`를 던진다(기존 에러 코드 유지). 401·403·쿼터 소진은 즉시 실패(재시도·헤징 안 함).
- 세마포어: 헤징으로 한 문장이 슬롯 2~3개를 쓰지 않도록 슬롯은 문장당 1개로 잡고 내부에서 요청을 늘린다.
- 취소(끼어들기 `task.cancel()`)는 모든 진행 중 요청을 취소한다. 취소 전파 테스트를 반드시 추가한다.
- `tts-1`은 `instructions`를 받지 않는다(`tts.py` `_style`이 이미 모델 이름으로 분기). 보이스 이름 지원 범위는 구현 때 OpenAI 문서로 확인한다.
- 관측: 대체 모델이 쓰인 비율을 로그로 센다(예: 문장 5%를 넘으면 말투 약화 체감이 늘므로 재검토).
