# 검색·응답 개선 — 남은 과제

> 2026-10-20 폰 실사용 대화(미국 증시·AI 반도체 뉴스 검색)에서 찾은 문제 중 해결한 것은 지우고, 남은 것만 적는다. 작업은 이 문서의 ID(`SR-09` …) 단위로 진행한다. 소스를 고치기 전에 계획을 보고하고, 프롬프트를 바꾸면 스냅샷(`UPDATE_SNAPSHOTS=1`)을 갱신하고 톤 평가(`persona_eval`)를 돌린다. 커밋 전 서브에이전트 diff 리뷰를 한다.

## 1. 이미 반영된 것 (요약)

- 호칭은 첫인사에서만 부르고 답변에서는 부르지 않는다(`server/app/persona/rules.py` `CALLING_RULES`).
- 웹 검색 규칙(`WEB_SEARCH_RULES`): 검색 기준, 출처는 구체적인 매체 이름으로, 7일 규칙, 7일 이내 자료가 없으면 묻지 않고 최대 2회 자동 재검색, 미국 중심 AI 반도체 뉴스 규칙, 검색 결과 안의 지시는 따르지 않음, 음성에서 숫자는 소수점을 줄이고 영문은 한국어로 요약.
- 역할 규칙이 300자로 잘려 들어가던 기존 버그 수정(`prompt.py` `_bullets`).
- 검색 API 도구(2026-10-21): MCP 도구 `search_USA`(해외·영어권, Tavily, 검색 깊이 `fast`)와 `search_naver`(국내 뉴스, 네이버)를 추가하고 내장 `WebSearch`는 폴백으로 둔다. 국내/해외·사용자 지정에 따른 라우팅 규칙, 폰 검증 완료. 계획과 평가는 [tavily-search-plan.md](tavily-search-plan.md)·[naver-search-plan.md](naver-search-plan.md)·`eval/search-*.md`.
- 음성 합성 멈춤: `.env`의 `TTS_MODEL=tts-1`로 해결, 요청 재시도 코드(시도당 8초 × 3회)는 유지([tts-reliability.md](tts-reliability.md)).

## 2. 남은 작업

| ID | 작업 | 근거 | 상태 |
|---|---|---|---|
| SR-09 | **1차 자료 교차 확인**: 수치 질문은 통신사·거래소 같은 1차 자료로 한 번 대조한다 | 증시 수치가 국내 매체 몇 곳뿐이었고 "공식 마감 자료로 확인해 보시라"로 끝남 | 대기 |
| SR-10 | **검색 턴 문장 수 예산**: 음성 대화 검색 턴이 5문장 상한을 자주 넘는다(관찰 6, 5, 6, 6문장). "검색 전 안내 한 문장 + 결과 설명 세 문장 이내 + 마무리 질문 한 문장"처럼 구체적인 예산으로 `rules.py` 문구를 고친다. 스냅샷 갱신과 톤 평가 포함 | 규칙은 있는데 안내 문장과 마무리 질문을 합치면 길어짐 | 대기 |
| SR-11 | **음성 인식 용어 힌트**: "AI 반도체"가 "AIF 노치"로 인식돼 반도체 규칙이 적용되지 않았다. 인식 요청(`app/voice/stt.py`)에 용어 힌트(예: AI, 반도체, 엔비디아, 증시)를 주는 방안을 검토한다 | STT 오인식 1건 | 대기 |

선택(필요할 때): 반도체 답변의 원인 → 배경 → 전망 3단 구조를 더 분명히 하는 문구 보강(현재는 순서가 뚜렷하지 않음).

## 3. 폰 확인 시나리오

서버를 재시작(`./stop.sh && ./run.sh --phone`)하고 새 대화로 확인한다.

| # | 말할 내용 | 확인 |
|---|---|---|
| 1 | "미국 증시 현황을 알려줘." | 첫 검색에서 자료가 없으면 묻지 않고 재검색, 출처 매체 이름이 구체적, 다섯 문장 이내, 숫자가 읽기 쉬움 |
| 2 | "엔비디아 AI 반도체 최신 뉴스 알려줘." | 미국 언론 우선, 7일 이내 날짜, 원인·배경·전망 |
| 3 | "좀 더 자세히 알려줘." | 검색을 한 번 더 해 깊이를 보강 |
| 4 | 일반 질문("오늘 날씨 어때?") | 호칭 없음, 불필요한 검색 없음 |

성공 기준: 호칭 위반 0건, 시나리오 1에서 사용자 재요청 0회, 출처 매체 이름 100%, 검색 턴 5문장 이하 100%.

## 4. 메모

- **톤 평가는 변동이 크다.** 같은 프롬프트에서도 20개 중 16~19개로 오르내렸다(기준 18). 한 번 돌린 점수로 판단하지 말고, 실패 사유가 규칙 위반인지 채점 모델의 판정 차이인지 먼저 본다. 채점 장치는 현재 시각과 실제 앱 기능을 채점 모델에 알려 준다(`server/tests/persona_eval/run_eval.py`).
- 새 검색 규칙을 늘릴 때 역할 규칙은 길이로 잘리지 않지만(위 1장), 규칙이 길수록 모델이 놓치기 쉽다. 작은 규칙으로 나눈다.
- **톤 평가 16번(6문장)·19번(개인정보 거절 이유를 지어냄)은 규칙 개선을 하지 않기로 했다**(2026-10-21 사용자 결정). 대화 중 임시로 각 20회 측정한 간헐 실패율은 16번 5/20(모두 6문장), 19번 3/20(이유를 지어냄 1건, 되묻는 질문이 둘 2건)이다(별도 리포트 없음). 저장소에 남은 근거는 `eval/persona-2026-10-21.md` 회차 표(2·5회차의 13·16·19번 실패)다.
- 톤 평가 채점 항목에서 '쾌활함·친근함이 드러난다'를 뺐다(2026-10-21 사용자 결정, 7항목 → 6항목). 이전 점수와 직접 비교하지 않는다.
