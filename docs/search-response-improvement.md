# 검색·응답 개선 계획서

> 상태: 초안(2026-10-20). 폰 실사용 대화 1건("미국 증시 현황" 검색, 제니 답변 7턴)과 서버 로그를 검토해 찾은 문제를 정리하고 개선 작업을 나눈다. 작업은 이 문서의 ID(예: `SR-01`) 단위로 진행한다.
> 규칙: 소스를 고치기 전에 계획을 보고하고, 프롬프트를 바꾸면 스냅샷을 갱신하고 톤 평가(`persona_eval`)를 다시 돌린다. 커밋 전 서브에이전트 diff 리뷰를 한다(저장소 `CLAUDE.md`).
> 범위 밖: 답변 시간 단축(V2 M1)은 계획에서 제외되어 있다. 이 문서의 SR-07(음성 합성 시간 초과)은 속도 개선이 아니라 **소리가 빠지는 신뢰성 문제**를 다룬다.

## 1. 근거 (관찰한 사실)

| 항목 | 값 |
|---|---|
| 대화 | 세션 `f2a3…`, 2026-10-20 22:16~22:23(KST). 사용자 질문 8개, 제니 답변 7턴, 검색 턴 5개 |
| 적용 규칙 | 호칭 규칙, 개정 웹 검색 규칙(커밋 `7381d34`, `e773920`) |
| 호칭 위반 | 0건 (첫인사에서만 "다니엘") |
| 5문장 상한 초과 | 7턴 중 4턴 (7, 7, 7, 8문장). 검색 전 안내와 결과가 한 턴에 합쳐짐 |
| 음성 합성 시간 초과 | `tts_timeout` 13건, 합성 대기 4.7~51초, 한 턴 완료 16~56초 |
| 사용자 끼어들기 | 2회(`trimmed`). 긴 대기 중 사용자가 이어 말하거나 끊음 |
| 사용자 재요청 | 검색 결과가 없거나 오래돼 사용자가 세 번 "찾아봐"라고 요청 |
| 제니가 쓴 검색어 | "미국 증시 2026년 10월 20일 나스닥 S&P500 다우", "How major US stock indexes fared Monday 10/19/2026", "AP how major US stock indexes fared Monday October 19 2026", "BBC 미국 증시 뉴욕 증시 마감 2026년 10월 19일 월요일" |

잘 된 점: 앱 날짜(10월 20일)로 사용자의 착오("21일")를 바로잡음, 자료가 없을 때 "최근 7일 이내 자료는 찾지 못했어요"를 먼저 말함, 블로그 한 곳의 수치는 공식 수치와 대조하라고 덧붙임, URL·마크다운 노출 없음.

|---|---|---|---|---|
| S1 | 첫 검색에서 포기하고 되묻는다 | 7일 이내 자료가 없을 때 "다른 검색어로 한 번 더 찾아볼까요?"로 끝났고, "더 깊이 찾는" 시도 뒤에야 10월 19일 수치를 찾음 | 재검색 규칙이 "사용자가 부족하다고 하면"(반도체 규칙 안)에만 걸려 있음 | 프롬프트 |
| S2 | 출처를 뭉뚱그린다 | "여러 국내 매체가 같은 수치를 전했는데"만 말함. 사용자가 물은 뒤에야 5곳 이름을 말함 | "매체 이름을 말한다"가 "여러 매체"로도 지켜진다고 해석됨 | 프롬프트 |

| S5 | AI 반도체 뉴스 규칙을 아직 검증하지 못함 | 이번 질문은 일반 증시 | - | 검증 |

| R2 | 검색 안내가 중복될 수 있다 | 모델이 "잠깐 찾아볼게요!"를 말하고(`prompt.py` 음성 블록), 서버도 `search_notice` 음성을 따로 재생 | 두 장치가 같은 일을 함 | 프롬프트/서버, 확인 필요 |
| R3 | 숫자·영문을 그대로 읽게 한다 | "26,430.89"처럼 소수점 숫자 나열, 영문 검색어를 길게 읽음 | 음성 읽기 규칙이 검색 답변에 약하게 적용됨 | 프롬프트 |
| R4 | 의도가 분명한데 되묻는다 | "19일 마감 숫자인지, 최근 흐름 전체인지" 되물음 | S1과 같음 | 프롬프트 |
| T1 | 음성 합성이 자주 시간 초과 | `tts_timeout` 13건, 3번째 턴은 첫 문장 합성이 15초(제한)에서 끊겨 첫 소리가 늦음. 합성에 실패한 문장은 소리가 나지 않음 | OpenAI 합성 호출 지연·시간 초과 제한 15초, 재시도 없음 | 서버 |

## 3. 개선 작업

### 3.1 1단계 — 프롬프트 수정 (SR-01~04)

모두 `server/app/persona/rules.py`의 규칙 문구를 고친다. 캐릭터와 무관한 앱 규칙이므로 YAML은 건드리지 않는다.

| ID | 작업 | 해결하는 문제 | 상태 | 커밋 |
|---|---|---|---|---|
| SR-01 | **자동 재검색**: 시점이 중요한 검색에서 7일 이내 자료가 없거나 날짜가 맞지 않으면, 묻지 말고 검색어를 바꿔(날짜·영문 제목 형식·다른 매체) 한 번 더 찾은 뒤 답한다. 그래도 없으면 그 사실과 가장 가까운 시점을 말하고 끝낸다(무한 재시도 금지, 최대 2회). 이 규칙은 반도체 규칙 밖의 일반 검색 규칙으로 둔다 | S1, R4 | 대기 | |
| SR-02 | **출처를 구체적으로**: "여러 매체"처럼 뭉뚱그리지 말고 실제 매체 이름을 말한다. 이름을 모르면 모른다고 한다 | S2 | 대기 | |
| SR-03 | **검색 턴 문장 수**: 검색 전 안내와 결과를 합쳐 다섯 문장 이내(음성 대화). 검색 전 안내는 한 문장으로 끝낸다 | R1 | 대기 | |
| SR-04 | **음성 읽기**: 검색 결과의 숫자는 소수점을 줄이고 퍼센트 위주로 말한다. 영문 검색어·제목은 읽지 않고 한국어로 요약한다 | R3 | 대기 | |

완료 조건
- 스냅샷 5개를 `UPDATE_SNAPSHOTS=1`로 갱신하고 차이가 의도한 변경뿐임을 검토한다.
- `tests/test_prompt.py`의 문구 단언이 새 규칙(재검색, 구체적 매체 이름, 합산 문장 수, 숫자 읽기)을 확인한다.
- 톤 평가 20개 중 18개 이상(호칭 실패 0건 유지).
- 폰 시나리오(4.1절)에서 재요청 없이 끝난다.

## 4. 검증

### 4.1 폰 시나리오

서버를 재시작(`./stop.sh && ./run.sh --phone`)하고 새 대화로 진행한다. 제니 답변은 `watch_replies.py` 같은 감시로 호칭·문장 수·URL·마크다운을 점검한다.

| # | 말할 내용 | 확인 |
|---|---|---|
| 1 | "미국 증시 현황을 알려줘." | 첫 검색에서 자료가 없으면 묻지 않고 재검색(SR-01), 출처 매체 이름이 구체적(SR-02), 다섯 문장 이내(SR-03), 숫자가 읽기 쉬움(SR-04) |
| 2 | "엔비디아 AI 반도체 최신 뉴스 알려줘." | SR-06 항목 전부 |
| 3 | "좀 더 자세히 알려줘." | 검색을 한 번 더 해 깊이를 보강 |
| 4 | 일반 질문 2개("오늘 날씨 어때?", "산책 코스 추천해 줘") | 호칭 없음, 검색하지 않아야 하는 질문에 검색하지 않음 |

### 4.2 성공 기준

| 기준 | 목표 |
|---|---|
| 호칭 위반 | 0건 유지 |
| 검색 후 사용자 재요청 | 시나리오 1에서 0회 |
| 출처 | 검색 답변마다 구체적 매체 이름 100% |
| 검색 턴 문장 수 | 5문장 이하 100% |
| 톤 평가 | 20개 중 18개 이상 |
| 합성 시간 초과 | SR-07 이후 대화 1건에서 `tts_timeout` 0건에 가깝게(기준은 SR-07 조사 뒤 확정) |

## 5. 순서

1. SR-01~04를 한 커밋으로 묶어 진행한다(스냅샷·톤 평가 한 번).
2. 폰에서 시나리오를 돌려 SR-05, SR-06을 확인한다.
3. SR-07(합성 시간 초과)과 SR-08(검색 도구)은 사용자가 방향을 정한 뒤 시작한다.
